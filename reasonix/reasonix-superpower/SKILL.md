# Superpower — 系统化 AI 开发工作流

**Superpower 是一套完整的开发方法论**，覆盖从创意到合入的每个环节。

## 1. 🧠 Brainstorming — 设计先于实现

**在展示设计并获得用户批准之前，不得写任何代码或采取实现动作。**

1. 探索项目上下文（文件、提交、文档）
2. 一次一个提问澄清需求——目的/约束/成功标准
3. 提出 2-3 种方案，带权衡分析和推荐
4. 展示设计，每节获得确认
5. 写设计文档到 `final/YYYY-MM-DD-<topic>-design.md`
6. 自审：占位符、矛盾、歧义、范围
7. 用户审查规格文件
8. 创建实施计划

## 2. 📝 Writing Plans — 编写实施计划

写全面、可执行的计划，假设执行者零代码库上下文。

- 先规划哪些文件被创建/修改、每个文件的职责
- 每个步骤一个动作（2-5 分钟）
- 禁止的占位符：❌ "TBD"、"后面补充"、"类似任务 N"

## 3. 🏗️ Subagent-Driven Development — 子 agent 驱动开发

**核心模式：每个任务一个全新 subagent + 两阶段审核（spec 合规 → 代码质量）**

1. 读计划文件，提取所有任务到 todo list
2. 每个任务循环：派发 implementer（Hermes: `delegate_task`）→ Spec 合规审核 → 代码质量审核 → 修复 → 标记完成
3. 所有任务完成后 → 最终整体 review

### Hermes 适配说明
此 skill 原为 Reasonix 设计。在 Hermes 中使用时适配如下：
- `explore` → 用 `delegate_task(goal, context, toolsets=['terminal', 'file'])`
- `todo_write` / `complete_step` → 用 `todo` 工具
- `subagent` → 用 `delegate_task`（batch 模式最多 3 个并行）
- `review` 工具 → Hermes 用 `delegate_task` 派发 review 作为独立子任务

### 模型选择
- 机械实现（1-2 文件）→ 快速模型
- 多文件集成 → 标准模型
- 架构/审核 → 最强模型

## 4. ✅ Verification Before Completion — 先验证再声称

**铁的法则：** 没有最新验证证据就不能声称通过。
1. 识别：什么命令能证明这个声称？
2. 运行：完整执行
3. 阅读：完整输出、检查退出码
4. 验证：输出确认了声称？
5. 然后才做声称

## 5. 🐛 Systematic Debugging — 系统化调试

**铁的法则：** 不完成根因调查就不准提修复方案。
1. **根因调查**：读错误→稳定复现→检查近期变更→追踪数据流
2. **模式分析**：找工作正常的例子、完整读参考实现
3. **假设与验证**：单一假设→最小改动验证→每次只变一个变量
4. **实施修复**：先写失败测试→只修根因→验证

## 6. 🔴 Test-Driven Development — 测试驱动开发

**铁的法则：** 没有失败测试在先，就不准写产品代码。
- **RED**：写一个最小失败测试，看着它失败
- **GREEN**：写最简代码通过它，看着它通过
- **REFACTOR**：保持绿，清理代码

### 核心分工：你写逻辑，AI 写测试

不要让 AI 写所有产品代码，然后你去逐行审阅。更高效的分工：

| 谁写 | 写什么 | 为什么 |
|------|--------|--------|
| **你** | 核心逻辑（5-20 行） | 你懂、能掌控、一眼定位问题 |
| **AI** | 测试（覆盖 100 种边界情况） | AI 擅长穷举你没想到的场景 |
| **AI** | 模板/样板代码 | 重复劳动，没人关心 |
| **你+AI** | 调试 | AI 定位根因，你判断方向 |

**工作流示例：**
1. 你手写 2 行核心函数 → 你确定它是对的
2. 让 AI 写测试：正常路径、边界值、空输入、异常文件、大流量、并发
3. 跑测试 → 全绿说明功能覆盖够了
4. 跑挂了一条 → AI 告诉你"测试 X 挂了，根因是 Y" → 你决定修逻辑还是修测试

### 排查 Bug 不靠逐行读码

出问题时按此优先级：
1. **让 AI 自查** — 把报错堆栈给 AI，让它定位根因
2. **分层检查** — 只关注负责的层（业务逻辑 > API > 数据 > 基础设施）
3. **定向查看** — 只看关键行（入口/出口、异常处理、配置项、API 调用、数据流向），模板代码跳过
4. **测试兜底** — 测试跑通 = 95% 没问题，不需要逐行审阅

## 7. 🔍 Requesting Code Review — 请求代码审查

每个 subagent 任务后、完成主要功能后、合并前必须审查。

## 8. 🎯 Finishing a Branch — 完成开发分支

测试通过后展示选项：合并到主分支、推送创建 PR、保留分支、丢弃。
