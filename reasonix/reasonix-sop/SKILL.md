# 00-SOP — 任务执行标准流程

**优先级: HIGH** — 每次会话开始和处理任何任务时强制执行。

## ⚠️ 铁律：先加载，再干活

在动手做任何事之前，**必须先调用 `skill_view('reasonix-sop')` 加载本文件**。不要凭记忆执行——即使你"记得"步骤，也可能跳步。本 session 已验证：跳过加载 = 被用户指出来纠正。

## 流程

### 第 1 步：澄清需求（用中文）

用户是中文母语者，用中文复述需求。在动手前确认：
- 用户真正的目标是什么？（不是表面需求，是背后的意图）
- 预期产出是什么？（文件、回答、分析、代码？）
- 有什么约束条件？（格式、风格、时间、范围？）

> *不要猜测，不要假设。用 1-2 句话复述你的理解让用户确认。*

#### ⚠️ 陷阱：用户说"肯定在"的东西，先自己查，不要问"在哪"

**被反复纠正过：** 当用户说"我的 xxx 肯定在某个地方 / 我肯定登录了 / 我记得有"时：

❌ 错误的做法：
- "在哪里啊？我怎么找不到？"（把问题抛回给用户）
- "我查了一下没有，你确认吗？"（质疑用户）

✅ 正确的做法：
1. 先穷尽自己能用的所有工具去查（gh CLI、文件系统、session_search、浏览器、search_files）
2. 换不同路径/不同方式再查一轮
3. 所有工具都查过还是找不到 → 汇报"我查了 A、B、C 都没找到，能指点一下方向吗？"

### 第 2 步：扫描全部 skill 源

扫描**两个来源**的全部 skill，合并判断可用 skill：

**来源 ①：Hermes 内置 skill** (hermes skills list，含 `reasonix-` 系)

**来源 ②：`skill-intros/`**（手写简介，≤15 行/条）
读取该目录下全部 `.md` 文件，快速了解每个 skill 的定位。

**来源 ②：`skills/`**（Anthropic/Agent Skills 文件夹格式）
读取该目录下每个子文件夹中的 `SKILL.md`（含 YAML frontmatter `name` + `description`），按文件夹名识别 skill。

扫描后判断：
- 当前任务有没有可以直接使用的 skill？来自哪个来源？
- 如果有，是哪个/哪些？怎么调用/触发？
- 如果多个 skill 可组合使用，规划组合顺序

> *这是强制步骤，不准跳过。哪怕你觉得"这个任务肯定不用 skill"。本 session 已验证：跳过了 skill 扫描 → 用户发现 last30days 没被正确使用 → 被纠正。*

### 第 3 步：判定适用 skill 和 profile，规划步骤

先扫描两样东西：

**① 适用 skill：**
- 若找到适配 skill → 列出调用路径和使用方式
- 若找不到适配 skill → 说明"无现有 skill 可用"，然后规划常规执行步骤

**② 适用 profile：**
- 用 `hermes profile list` 查看所有可用 profile
- 判断：当前任务有没有能分担的 profile？（researcher 调研、coder 写代码、reviewer 审查、gangjing 找茬等）
- 若找到 → 在执行计划中写明哪个步骤交给哪个 profile，用 `kanban_create(assignee="profile名")` 创建任务卡片，由 Kanban Dispatcher 自动唤醒对应 profile 执行
- 若找不到 → 说明"无适配 profile"，自己执行全部步骤

> ⚠️ **Hermes Studio WebUI 群聊功能（GroupChat）不可用。** 数据库表和 WebSocket 连接存在，但消息分发引擎未实现，agent 不会响应群聊消息。详见 `references/hermes-webui-groupchat.md`。如需多 profile 实时对话，用 Telegram 群 + 各 profile 独立 gateway。

最后用 `todo_write` 列出详细执行步骤（颗粒度：每步一个可验证的操作），
**每个步骤必须标注执行者**（自己 or 哪个 profile）。

### 第 3.5 步：复杂度检查（KIM 法则）

**在规划具体实现方案之前，必须先做复杂度检查。** 用户多次纠正过这个模式：

核心原则（KIM 法则）：**先问"最简单的做法是什么"，而不是先介绍复杂的方案。**

✅ 正确的顺序：
1. 先问："你需要的是不是一个简单的命令/脚本/skill就能搞定的？"
2. 如果是 → 给出最简单的方案（一行命令，一个 skill 指令）
3. 只有当简单方案明确不够用了，再提复杂方案（RAG、数据库、基础设施等）

❌ 错误的顺序（被用户纠正过）：
1. 一上来就介绍 R2R、RAG、向量数据库等复杂方案
2. 用户反问"不就是一个命令的事吗？"
3. 被迫绕回来承认简单方案更好

**什么时候用简单方案：**
- 文档/数据量在几十个文件以内 → 一个 skill 指令 + 手动目录就够了
- 用户问的是"能不能做某事" → 先回答"能"并给出最简单的做法
- 调研/信息查询类任务 → 直接用现有工具完成，不需要搭系统

**什么时候该提复杂方案：**
- 用户明确问了"企业级怎么做"
- 数据量在万级以上，人力无法管理
- 用户自己提到了"RAG""向量数据库"等词

> *这条被多次触发纠正，不准跳过。即使你觉得"这个场景确实需要复杂方案"，也要先提一句简单方案再对比。*

### 第 4 步：执行
逐步骤执行。
- 标记给自己的任务 → 自己完成，每步用 `todo_write` 记录进度和证据
- 标记给其他 profile 的任务 → 用 `kanban_create` 创建任务卡片（指定 assignee），由 Kanban Dispatcher 自动调度对应 profile 执行，通过 `kanban_show` 追踪完成状态，拿到产出后验收

### 第 5 步：完成检查
- 产出是否符合第 1 步确认的需求？
- 所有步骤是否都有完成证据？（自己做的 + 委派给其他 profile 的）
- 委派给其他 profile 的产出是否经过验收？（不能盲信，必须核实）
- 是否需要更新 `memory-box` 记忆？
- **技术术语是否解释清楚了？** 如果产出包含专业术语，必须逐个用大白话+比喻解释。

## 📐 沟通风格守则

**用户的风格偏好（被多次纠正，铁律）：**

1. **说人话，不说术语缩写** — 用户问"Postgres是什么"是想知道它**干什么用的**，不是要英文全称。用比喻：Postgres = "存表格数据的地方，像Excel但给电脑程序用的"。RAG = "开卷考试"。Agent = "能自己决定怎么干活的AI"。
2. **简短直接，不铺垫** — 用户不要"首先让我们了解一下..."这类过渡。直接给答案。如"这东西跟SQL有什么区别" → 直接说"SQL查完全匹配，RAG查意思相近的"。
3. **用户问什么答什么** — 不要扩展解释用户没问的内容，除非用户追问。
4. **承认错误** — 解释错了直接说"前面我说错了"，不要找补。

**触发：** 每当你需要向用户解释一个技术概念时，先想比喻，3句话内说完，然后问"够清楚了吗？"

### ⚠️ 陷阱：英文缩写 ≠ 解释（被纠正）
**被纠正的经历：** 用户说"我让你解释这几种名词的意思，是我看不懂这些专业名词是什么意思，并不是说让它的英文版本"。

当用户问"XXXX是什么/什么意思"时：
- ❌ 先答"XXXX = Xxx Xxx Xxx 的缩写"（英文全称）→ 用户要的不是这个
- ✅ 直接说"它是干什么用的" → **功能比喻优先**，用最日常的东西类比

例：
- ❌ "SoTA = State of The Art的缩写，意为最先进水平"
- ✅ "SoTA就是当前这个领域里最好的水平，跟'顶配'差不多意思"

规则：**用户问名词解释 = 告诉他这玩意是干嘛的，不是告诉他缩写全称。**
